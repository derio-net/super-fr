# Explainers currency — the published site must not lag the code

## Rule

`docs/explainers/` is published to **https://derio-net.github.io/super-fr** by
`.github/workflows/pages.yml`, on every push to `main` that touches
`docs/explainers/**`. It is the only outward-facing prose super-fr has.

**A PR that changes behaviour an explainer describes updates that explainer in
the same PR**, or records in the PR body why it does not. Triggers:

- a shipped skill's pipeline or surface changes (`plugins/*/skills/**`);
- a new CLI verb, or a changed one an explainer names;
- a shipped default changes (a manifest, a resolution order, a gate);
- a **minor or major** version bump — patch fixes with no user-visible surface
  do not trigger this.

Internal refactors, test-only changes, and anything invisible to a reader who
does not work on this repo are explicitly *not* triggers. The test is whether a
newcomer reading the published page would now be misled.

## The trap: editing the `.md` does not update the site

Each page is a pair — `01-fr-goal.md` (prose source) and `01-fr-goal.html`
(what Pages actually serves). **The `.html` is generated by an external
blog-craft pipeline that does not exist in this repo** (its own header points at
`tools/fetch_broadsheet_fonts.py`, which lives elsewhere), and it is the file
that ships. A PR that edits only the `.md` looks complete, passes every gate,
and leaves the published page stale — the failure mode this repo keeps
producing in other forms: a change that reports success while doing nothing.

So a compliant PR either regenerates the `.html` alongside the `.md`, or states
plainly that the regeneration is owed and the site is knowingly behind.

## Regenerating a page

The pages are produced by the **`blog-craft:explainers`** skill; the renderer is
`tools/render_explainer.py` in the blog-craft plugin. From the repo root:

```bash
B=~/.claude/plugins/cache/derio-net--blog-craft/blog-craft/<version>
uv run --no-project --with markdown --with pyyaml python "$B/tools/render_explainer.py" \
  docs/explainers/<name>.md --style broadsheet --embed-fonts \
  -o docs/explainers/<name>.html
```

`--style broadsheet --embed-fonts` is what produced the committed pages — the
style is also declared per-page as `standalone_style:` in the front matter, so
check there before assuming. The renderer imports `markdown` and `yaml` but
declares neither, hence `--with`; without them it aborts cleanly and leaves the
existing page untouched, so a failed render cannot half-write a page.

Pin `<version>` to whatever is installed; the path is a plugin cache, so a
blog-craft upgrade moves it. If the command above stops resolving, that is the
signal to re-derive it, not to hand-edit the HTML.

## Enforcement

`tests/unit/test_tripwire_explainers_fresh.py` fails when a rendered page stops
carrying its source's title or any of its section headings. It is a heuristic by
necessity — the renderer lives in another repo, so CI cannot re-render and diff —
but it catches the realistic failure: prose restructured, page never
regenerated. It also pins the set of pages with no committed source as a closed
set, so a third one cannot appear unnoticed.

## Known gaps

1. **`index.html` and `fr-isolation.html` have no committed `.md` source** — only
   `01-fr-goal.md` does. Those two pages can only be edited by whoever holds
   their source, which is not this repository, and the tripwire can therefore
   check nothing about them beyond their continued existence. Bringing their
   sources in is owed.
2. **The tripwire cannot prove a page is fully current** — only that its
   headings and title survived. Prose edited within an unchanged section will
   not be caught. Closing that would mean either vendoring the renderer or
   recording a source hash in the rendered page at render time.

## How to apply

Edit the `.md`; match the existing voice — second person, concrete, unhurried,
explaining *why* a mechanism exists rather than only what it does; it is written
for a reader who has never seen this repo. Then regenerate the `.html` and
commit both. Never hand-edit the `.html`: it carries base64-embedded fonts and a
"do not hand-edit" banner, and a manual patch there will be silently overwritten
by the next regeneration.
