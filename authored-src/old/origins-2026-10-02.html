Found or made? Where super-fr's new issues came from

Over six days, the issue count climbed as fr's own runs, walks and the talk recordings exercised it. That looks like a bug machine. Classifying each issue by origin says otherwise: 42 were latent defects that new usage exposed, and 5 were regressions, plus 2 more fixed without an issue. What grew was volume: out-of-scope findings filed by fr's own reviews (33), and first defects of large new features (25). Take 10's live walk (#817) added a harder finding: six fixes that closed their issue in CI failed or only partly held in a live run. The operator's answer was to cut the layer those fixes guarded: 11 of the issues were about the input layer itself, and 5.0.0 removed it.

5.0.0 · the cut

The input layer answered one defect and filed eleven more

#759 found that fr-goal paraphrased the operator's brief into the spec and never checked it. #762 answered with a requirements table that had to quote the brief, and each live run then found the next place the brief could be lost. Seven PRs (#762, #786, #788, #791, #819, #827, #833) grew four derived gates, a reviewer agent and three journal tokens. Take 10 showed them passing on OpenCode with a made-up reviewer, and one run spent 31 minutes on 13 spec-review dispatches inside the coverage loop (#808). The operator's decision was that the input feeds the brainstorm and nothing else. 5.0.0 removed the layer.

Eleven of the 142 issues filed since 09-24 were about the layer itself. Seven closed as moot when it was cut, and four were fixed by PRs whose code went out with it. Each fix opened the next issue: the gates of #762 gave #764, #776, #777, #778 and #808, and the fidelity check of #819 gave #829, #830, #846 and #847. #846 is the sharpest: the live test of #773 showed invented behaviour still shipping, because the executor added it after the check had run.

The lesson is about where a fix goes. Every one of these guarded a copy of the input downstream of the step that owns it. Making the spec the contract moves the check to the one place a person reads it, and a requirement the spec omits is a spec defect, fixed there.

Reading

A filing and first-release problem, not a breakage problem

"Bug creation machine" overstates it. About 5–7 of 142 issues are real regressions. The largest share is old defects that new usage exposed: OpenCode, GitLab, macOS, the devcontainer, back-to-back batch merges.

What grows fast is volume. fr-goal's contract files every out-of-scope finding (33 leftovers), and big features ship with gaps only live runs find (25). The operator cancelled the in-run duplicate check (#781): a run should not search the backlog, so duplicates are left for an asynchronous sweep. That is where the process can improve: fewer, merged filings, and a live walk before a large feature is released. Take 10 is the evidence for that last point (see above).

The severe regressions escaped review. #683 (the test suite overwrote the operator's fr) and #742 (deliver could never resolve on GitLab) were both merged through fr's own review gates. Those gates check what the reviewer is shown; neither case was in front of it.

Method

How this was classified, and what wasn't verified

  • Every issue created on or after 2026-09-24 was listed with gh and its body read; provenance lines ("found in review of #x", "closeout", "live walk", "take N") give the source.
  • For each candidate regression or new-feature defect, the faulty symbol was traced with git log -S on origin/main to the PR that introduced it.
  • Issues that say "pre-existing" were taken at their word unless git contradicted them. About 20 of those claims were spot-checked with git, not all.
  • Unfiled regressions were found only by searching PR bodies for "regress", so there may be more.
  • Severity is the classifier's judgement; the issues carry no tier labels. Wave numbers past waves 1 and 5 are inferred.
  • Extension, 2026-09-29: the 22 issues filed after the first pass (#783–#821) were classified from their bodies and the #817 audit. The introducing PR is the one each body names; git was not traced for these. The states and closing PRs of all issues were refreshed from gh.
  • Second extension, evening of 2026-09-29: the 13 issues filed since (#822–#848) were classified from their bodies, including three from take 11. The set of eleven input-layer issues is read from the issue text. States were refreshed again, and the seven closed with the cut are marked as such.
  • Third extension, after the talk (2026-10-02): #854 and #855 were classified from their bodies. #854 (nothing tests the release commit) is a gap in the release design and was found live by take 12; #855 is two latent defects found while reviewing the ceiling fix. No other issue was filed or closed since 09-29.
