# Journal: 2026-08-26-hermes-hook-jq-lockout

### repro-lockout · repro · Hermes pre_tool_call hooks locked the agent out of its own terminal

On the hermes-agent-shell pod (frank cluster), Hermes could not run terminal/execute_code or edit files: every call came back with a hook decision of block. The three pre_tool_call hooks under /opt/data/super-fr-hooks/hermes/ call jq to read the payload. jq is installed on the PVC at the agent's ~/.local/bin/jq, which the gateway service PATH omits, so a bare `jq` resolved to nothing. Originally this aborted each hook under `set -eu` with exit 127 BEFORE any decision reached stdout, and the harness read the empty stdout as no opinion: all three guards had been silently disarmed. A hand-applied repair on the pod then added a fail-closed `command -v jq` preamble to fr-isolation-guard.sh (and the preamble only, not the body, to fr-isolation-required.sh). The PATH gap was unchanged, so the new refusal fired on every matched call and Hermes could no longer edit the hooks that were blocking it. Neither pod edit was ever committed: the repo copies still had the original bare-jq form.

<!-- fr:journal kind=root-cause scope=debug id=root-cause-path-lookup created=2026-08-27T10:35:53 -->
### root-cause-path-lookup · root-cause · The dependency was a PATH lookup, so both failure directions were wrong

The guards' correctness rested on a bare-word `jq` resolving through whatever PATH the harness happened to hand the hook. That is not a property the hook controls. Failing open (exit 127, no stdout) disarmed the policy silently; failing closed on the same unresolvable name locked the agent out with no in-band way to repair it, because the repair itself needs the tools the hook is blocking. The same PATH gap had already been seen and worked around once: the 2026-07-24 hermes-hooks-wrong-config journal records a broad suite run that excluded 'two installer modules whose hardcoded PATH cannot see this pod user-installed jq'. It was treated as a test-environment quirk rather than the hook dependency it is. The shared library lib/fr-isolation-decision.sh had the same latent bug in its marker parsing, so even a jq-resolving hook would have mis-validated a worktree marker if jq went missing.

<!-- fr:journal kind=finding scope=debug id=fix-parser-independence created=2026-08-27T10:36:06 state=fixed -->
### fix-parser-independence · finding [fixed] · Resolve the parser from absolute paths; make every failure an explicit decision

lib/fr-isolation-decision.sh gains fr_json_resolve / fr_json_field / fr_json_file_field. python3's stdlib json is preferred and probed at absolute paths (/usr/bin/python3 and friends), with a resolved jq as an independent second parser; both candidate lists are overridable via FR_PYTHON_CANDIDATES / FR_JQ_CANDIDATES, which also makes the no-parser branch testable. Marker parsing now goes through the same helper and fails closed on an unreadable or non-object marker. The three Hermes hooks source the library first, then refuse explicitly (a one-line JSON block on stdout, exit 0) for a missing library, an unresolvable parser, or an unparseable payload; a valid-JSON non-object counts as unparseable. Deny output is escaped with sed so emitting a refusal never needs the parser that is missing. Decision policy is unchanged: which commands count as mutations, cd-prefix cwd resolution, marker validation and the .fr-isolation-allow globlist are all as before, and the push guard still fails OPEN on every genuine PR-state ambiguity (no push, no PR, gh absent, non-fr repo, network error, unparseable gh output). gh remains confined to the push guard. Verified live on the pod under PATH=/usr/bin:/bin with no jq: read-only git allowed, base-clone mutation blocked, worktree mutation allowed, cd-into-worktree allowed, non-allowlisted base edit blocked, allowlisted path allowed, malformed and empty payloads refused explicitly at exit 0, and no jq: command not found in any hook invocation. Repo suite: 1862 passed, 80 skipped; 36 new tests in test_hermes_hooks_parser_independence.py.
