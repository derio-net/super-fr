### 30dcd781178d · decision · observe() keys by SCRIPT FILENAME, not surface_id - the independence is the point (phase 2)

The plan writes the signature as observe(repo_root) -> dict[surface_id, dict[harness, present|absent]]. Implemented as dict[script filename, ...] instead (fr-isolation-required.sh, not fr-isolation-required). Reason: an observer that had to return surface ids would have to READ parity.yaml to learn them, and at that moment the check stops being derived and becomes a transcription that can agree with itself. observe.py imports nothing from the matrix; check.py is the only bridge, through each hook row's script field. The two happen to differ only by the .sh suffix in today's data, which is exactly why keying on the id would have looked fine and been wrong. Pinned by tests/unit/test_harness_observe.py (all keys are filenames) and test_harness_check.py::test_a_hook_row_whose_script_was_never_observed_reads_as_absent.

<!-- fr:journal kind=decision scope=plan id=55ea8d391ec1 created=2026-09-18T15:55:16 phase=2 -->
### 55ea8d391ec1 · decision · codex and copilot-cli are UNOBSERVABLE, not observed-absent (phase 2)

observe() returns states only for OBSERVABLE_HARNESSES = (claude-code, opencode, hermes) - the three with a registration file. The tempting alternative (return absent for codex/copilot-cli too) would have been harmless today because every such cell is unsupported and unsupported never yields a finding, but it encodes silence as evidence: the day someone declares a codex cell enforced, check would report 'observed absent' from a file it never read. check() therefore iterates OBSERVABLE_HARNESSES, not HARNESSES. Consequence for later phases: adding codex support means adding one _Observer entry to observe.py's dispatch table (which also derives OBSERVABLE_HARNESSES and REGISTRATION_FILES - P2.T4.S2's refactor made those derived, not a second list), plus a reader for its registration file. Pinned by test_harness_check.py::test_the_unobservable_harnesses_never_produce_a_finding and test_harness_observe.py::test_the_observer_table_is_the_only_place_a_harness_is_declared_observable.

### bd7f8a053916 · discovery · check()'s five-state rule table, and why unsupported is a MISSING key rather than a mapped one (phase 2)

_EXPECTED_OBSERVATION in check.py maps declared state -> the registration fact it implies: enforced->present, partial->present, advisory->absent, absent->absent. unsupported is deliberately NOT a key: a missing key means 'makes no claim about registration, so no observation can contradict it'. Written as a lookup rather than an if/elif chain so a sixth state is one row. Verified against the two live cells the journal warned about: hermes/fr-isolation-guard is declared partial and IS registered in .hermes/config.snippet.yaml, so it comes out clean (test_declared_partial_and_observed_present_is_clean, which cites that exact cell); hermes/fr-acceptance-nag is declared enforced and observed present, so the #436 understatement is absent from this repo's matrix by construction. Interaction rows are skipped entirely - no registration file can speak to an interaction surface, so the matrix is the only record there is (test_interaction_rows_are_never_checked_against_observation).

### e517c9039bcf · discovery · --check writes through typer.echo, not the rich console (phase 2)

Finding r1-m6 (phase 1) showed rich snapshots COLUMNS at Console construction, which happens at module import, before any fixture can widen it - so an assertion on rendered output passes only at some widths. A finding message is one long line naming two file paths, i.e. exactly the shape rich would wrap.
