### p1-op-body-keys-in-journal-model · decision · OP_BODY_KEYS, op_body and op_fields live in fr.journal.model beside OWED_FIELDS (phase 1)

The writer (`op_body`, used by `fr.ops.evidence.record_op`) and the fold
(`op_fields`, used by `fr.ops.evidence.fold`) read the one constant. `op_body`
refuses an unknown key, a missing op/result, an unknown result and any
multi-line value. Appending an `op` entry stamps an older journal at the
current version in the same write (`_at_current_stamp`, formerly
`_at_owed_stamp`).

<!-- fr:journal kind=decision scope=plan id=p1-status-semantics created=2026-10-22T07:56:12+00:00 phase=1 -->
### p1-status-semantics · decision · How fr ops status reads the less obvious cases (phase 1)

`check: proof` reports DONE (proof), a label beside checked/attested/legacy.
A legacy `status: done` closes the op before any probe runs. `na_if` and
`escalate` run once with no identity env; `check` runs once per identity.
An op with `disables` never runs `na_if`. ESCALATE applies to OPEN,
UNVERIFIABLE and CANNOT-VERIFY, never to N/A. A checkless op is closed only
by an `attested` entry (a recorded `done` does not close it). Reasons are
cut to 200 chars and every identity value in them is masked. `status`
orders ops by `needs` and refuses (exit 2) a cycle or an unknown id.

### p1-op-kind-refusals · decision · A record refuses `op` by a field validator; fr journal add refuses --kind op (phase 1)

`JournalItem.kind` keeps the `JournalKind` type and a validator refuses `op`
(the record kind is unchanged, as R17 says). `fr journal add --kind op` exits 2
naming `fr ops` before any write: the record-validation path would otherwise
surface a raw pydantic traceback.

<!-- fr:journal kind=discovery scope=plan id=p1-floor-above-installed-unparseable created=2026-10-22T07:56:12+00:00 phase=1 -->
### p1-floor-above-installed-unparseable · discovery · A plan floored at 5.28.0 is unparseable by the 5.27.0rc3 in this tree (phase 1)

fr.parser refuses a plan whose fr_version floor is above the installed fr, so
no plan in this repo can carry ops with the required `>=5.28.0` floor until
5.28.0 (or an rc of it) is installed. The self-review floor test patches the
parsed meta instead of writing `_meta.yaml`. Phases 2-4 that dogfood ops on
a real plan in this repo hit the same wall.
