<!-- fr:journal kind=decision scope=plan id=p3-publish-token-scope created=2026-11-01T19:51:40+00:00 phase=3 -->
### p3-publish-token-scope · decision · publish gets GH_TOKEN only; the override rides in the plan (phase 3)

Only `prepare` computes what to release, so only it gets FR_RELEASE_STATUS_TOKEN and RELEASE_VERSION. `publish` reads the override from release-plan.json (so a superseded --version run knows to print `re-dispatch: gh workflow run release.yml -f version=<X>`) and gets GH_TOKEN alone, for its push, tag push and `gh release`/`gh issue`. Least privilege per job rather than copying today's one-step env to both.

<!-- fr:journal kind=decision scope=plan id=p3-collect-subcommand created=2026-11-01T19:51:40+00:00 phase=3 -->
### p3-collect-subcommand · decision · release.py gains a `collect` subcommand beside the four planned ones (phase 3)

So the release's collect job runs credential-free through `_credential_free_env()` like test-shard, and so both share one constant, `SHARD_ADDOPTS` (`-o addopts=--strict-markers`), which a test pins on both argvs: split-check only means something when collect and the shards use the same options.

<!-- fr:journal kind=discovery scope=plan id=p3-untracked-before-add created=2026-11-01T19:51:40+00:00 phase=3 -->
### p3-untracked-before-add · discovery · Release-job scratch files must stay out of the checkout until the release commit exists (phase 3)

`make_release_commit` runs `git add -A` and `verify_staged` refuses anything outside the version surfaces, so a durations cache restored into the workspace before `prepare` would refuse every release. The workflow restores the cache only after `release.py prepare` (gated on cut) and keeps the plan, bundle, collected list and shard durations under `runner.temp`.
