### input-brief · discovery · Operator brief: gh#1220 verbatim

# gh#1220: fr ops: manual-operation blocks become checkable/runnable (status, idempotent apply, pre/post-merge batches) for the devops gate

## Problem

A plan's `# manual-operation` blocks are prose. Nothing checks them. At `deliver` and at the post-merge close-out, the operator has to work out by hand which ops are done, which are still open, and in what order to run the rest. For anything behind a `devops` (or `tester`) gate, that is exactly where runs stall or go wrong.

## Evidence (derio-net/frank#878, #887)

frank#875 shipped with eight manual ops, split between PRE-MERGE and post-merge. The operator asked for "a script I can run to either implement them or show which ones are still open and verify the ones that are done". The ad-hoc answer was `scripts/ci-budget-ops.sh`:

- `status` is read-only. It reports every op as DONE / OPEN / N/A with live evidence.
- `apply <op>` is idempotent and confirms before acting.
- `apply pre-merge` and `apply post-merge` run the ops in batches.
- Its inputs come from the change's own config, not a hard-coded list.

It paid off at once. Its live checks caught five real defects that unit tests, three review rounds and CI all missed:

1. A token-permission key that does not exist (`variables` instead of `actions_variables`). Token minting would have failed once deployed.
2. A billing SKU name that the code did not know (`Actions macOS 3-core`). The watcher would have errored on every run.
3. A webhook secret whose secret-store value was never seeded. The ExternalSecret existed, but the triggers would have rejected every delivery.
4. A GitOps app stuck "Synced" at a revision from five days earlier. The post-merge guard caught that the merge had not been applied.
5. A semantics probe that could not prove what it claimed: its branch tip never touched the filtered paths.

Writing it by hand also produced its own bugs, which a standard feature would make once and fix once:

- A plaintext secret could be left in the checkout if encryption failed.
- `sops` creation rules match the input path, so encrypting a temp file failed.
- A probe interrupted by Ctrl-C left a scratch repo behind.
- A secret read failing inside `$(…)` under `set -e` exited silently.

## Proposal: manual ops become checkable and runnable (`fr ops`)

- **Schema.** Each `# manual-operation` block gains optional, machine-runnable fields:
  - `check:` — a read-only probe; exit 0 = done, otherwise open, with a one-line reason.
  - `apply:` — idempotent automation; omitted when the op is UI-only.
  - `phase: pre-merge|post-merge`, plus `needs: [<op-id>]` for ordering.

  `commands` / `verify` stay as human prose. An op with no `check` is reported "unverifiable — manual". It is never reported as done.
- **CLI.**
  - `fr ops status [--plan <dir>] [<op-id>]` lists DONE / OPEN / N/A / UNVERIFIABLE, with evidence.
  - `fr ops apply <op-id>` runs one op.
  - `fr ops apply --phase pre-merge|post-merge` runs a batch in dependency order. It confirms per op, and stops on the first failure, naming that op.
- **Pipeline wiring.**
  - At `deliver`, the PR body's "Pre-merge verification owed" and manual-phase sections are rendered from `fr ops status`, not hand-written. A PR with OPEN pre-merge ops carries that state, and the ready checklist shows it.
  - At the close-out brief (`fr pickup --run`), the post-merge step becomes `fr ops apply --phase post-merge`, then `fr ops status`.
  - The `devops` / `tester` gate's close-out reads `fr ops status`. The gate cannot be marked walked while a gated op is OPEN.
- **Post-merge readiness.** Post-merge ops need a "merge has landed" precondition that checks a live artifact, not the forge's merge state. Example: a resource that only the merged revision creates. The GitOps tool's "Synced" status is not enough; see frank's stale-revision gotcha.
- **Helpers, so op authors don't each reinvent the dangerous parts:**
  - Read secrets live and never print them.
  - Hold plaintext only in a 0600 temp file outside the repo, removed by an exit trap. Encrypt with `sops --filename-override <target>`, and write the tracked file only after encryption succeeds.
  - Put values on the clipboard instead of stdout when a UI paste is unavoidable.
  - Clean up scratch resources with an exit trap.
  - Every probe states what it would look like if it were vacuous. The paths-filter probe failure above is the model.
- **Runbook sync.** `/sync-runbook` carries `check` / `apply` into `manual-operations.yaml`, so `fr ops status` also works for ops from earlier plans. Example: the pre-existing op behind (3), which was still pending from an older plan.

## Acceptance

- `fr ops status` on a plan lists every manual op, with live state and a reason for each OPEN.
- `fr ops apply --phase pre-merge` and `--phase post-merge` are idempotent: a second run writes nothing, and reports so.
- `deliver` renders the owed pre-merge ops from `fr ops status`, and the gated close-out refuses while one is OPEN.
- The secret helpers never leave plaintext in the repo when encryption fails. This is tested.
- The reference implementation, frank's `scripts/ci-budget-ops.sh` (in #878 and #887), is replaced by `check` / `apply` fields on that plan's ops, as the first consumer.

## Comment 1

## More evidence from the post-merge close-out (frank#888, #889, #890, #891, #892)

The close-out session for the same run (`fr pickup --run …` followed by `fr-debugging`) found more defects while it walked the Test Plan and cleared the `devops` gate. Nearly every one is an op that a script or a person called "done" which a real `check:` would have shown OPEN. They are grouped below by the `fr ops` design point each one supports.

### 1. A `check:` must exercise the consumer's identity, not the admin's

- **Grants were missing for identities other than the one that ran the op.** The new orgs were provisioned with an admin token, and the admin-run `status` showed everything green. Two other identities were still locked out:
  - The read-only delivery checker reads as its own bot user, which was not a member of the new orgs, so it got 404 on 9 of 10 repos.
  - The mirror push identity had write access in one new org but not the other, so the reconciler failed for every repo in that org.

  An op's `check:` should run *as each consumer identity*, by actually reading or writing the resource, rather than inspecting membership as an admin. Onboarding a new org should list every identity that touches it.
- **A grant was applied to one of two orgs, and the status check had the same gap.** Per-org loops in `check:` and `apply:` should be generated from one list, so they cannot drift apart.

### 2. Failures must keep their reason

- **A bare `except` turned every failure into `read-error`, with no HTTP status.** Telling "not a member" (404) from "wrong default branch" (404 on a different path) from "token scope" (403) took a debugging session. Checks, and the CronJobs they verify, should log the status code, but never forge response text, which can leak.

### 3. Don't assume a repository's shape

- **A default branch other than `main` broke two CronJobs that hard-coded `main`.** The push-sync webhook filters also match only `main`, so that repo's branch is repaired by the 15-minute reconciler rather than synced on push. Ops helpers should read `default_branch` everywhere. The ad-hoc script already did; the shipped code did not.

### 4. Provisioning side effects need guards, and an undo path

- **The mirror backfill pushed every tag.** Gitea then ran the *old, pre-gate* tag-triggered release workflows: 8 runs and 54 jobs that queued for hours and starved the shared runner. The backfill also ran ungated test workflows on old commits, which left permanent "status delivery mismatch" noise in the delivery checker.
  - A backfill `apply:` should disable Actions on the target, push only what is needed, then re-enable Actions. Pushing branches first and tags never works too.
  - Onboarding order matters: status forwarding should be live before any CI can run on the mirror.
- **Gitea 1.25 cannot cancel a queued run through its API.** Deleting a queued run returns 400, so cleanup needed the admin web UI and a person. `fr ops` should document an undo for each `apply:`, and flag any apply whose side effects have no automated undo.

### 5. An optional dependency that disables a requirement must show as OPEN

- **The notifier's Secret was declared optional ("absent means heartbeat-only").** Nothing created it, and `status` reported 0 open items. So the requirement to notify on every flip, would-flip and refusal was silently off: refusals logged before go-live were sent nowhere. It was found only by reading the watcher code during the Test Plan.
  - A `check:` must report a disabled requirement as OPEN and name the consequence.
  - It was fixed by declaring the credential as an ExternalSecret from the existing secret store, rather than having a script copy it. `fr ops` should prefer declaring a dependency to provisioning it.

### 6. Proofs must be durable and shared, not local

- **The one-off semantics proof was stored in a gitignored file in one workspace.** The close-out session, working in a different workspace, saw the op as "not proven" and had to re-run it, creating and deleting a scratch repo again. Proof evidence belongs in the run's journal or evidence store, where `fr ops status` from any checkout can read it.

### 7. State-transition ops and the guards that pin the starting state

- **A tripwire test asserted that every org ships `mode: dry-run`.** So the go-live op, a one-line config PR, also had to edit the guard. An op that changes a pinned state should ship with the guard's transition rule, for example "dry-run unless listed in a go-live allowlist". Otherwise every go-live is a surprise test failure.

### 8. Manual-phase ticks and the archive gate should come from `check:`

- **The archive was held until Phase 6, the manual ops, had its steps ticked.** The session ticked them by hand, and only for steps whose `status` passed. That is the rule `fr ops` should encode: a manual step is ticked when its `check:` passes, never by assertion, and the archive gate reads the same source.

### 9. Test Plan steps belong in the same model, with ordering and approvals

- **Of the 10 Test Plan rows, several waited on the go-live flip and several needed explicit approval** (suspending a CronJob, scaling the runner to 0, creating a GitHub issue). Recorded outcomes cannot be rewritten, so later evidence went into a journal entry.

  Each Test Plan row could be an op with these fields:
  - `needs:` for ordering, e.g. "after go-live";
  - `mutating: true`, which requires approval;
  - `undo:`;
  - a `check:` that records `--ran` or `--owed` with a reason.
- **Throwaway artifacts created during verification need guaranteed cleanup** (a probe PR and branch, a scratch repo). This is the same exit-trap helper as before.

### 10. Status should escalate when reality gets ahead of the dry run

- **During the dry run, GitHub was already refusing one org's jobs for its spending limit,** while the watcher only reported `would-flip` at 97.7%. Nobody was notified, because the notifier was off (point 5). `fr ops status`, or the feature's own status, should escalate when the condition a go-live protects against is already happening.
- **The watcher's dry-run `refused` verdict looked like a bug during close-out.** It was correct: gate PRs in other repos had not merged yet. A `check:` result should carry its reason ("refused: N repos have gate-coverage gaps — waiting on their PRs"), so the operator doesn't have to debug a correct state.

### What this means for the design

Of the 9 defects in this round, 7 were invisible to tests, review and CI, yet visible to a check that runs as the real identity against the live system. The other two were the backfill side effects and the missing undo path. That strengthens the core proposal:
- a manual op counts as done only when its `check:` passes;
- checks run as the consumer identities;
- every `apply:` declares its side effects and its undo.
