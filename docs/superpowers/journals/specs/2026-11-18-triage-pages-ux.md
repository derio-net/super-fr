# triage pages: UX pass — consistent names, collapsible sections, cross-links, filters, and a History page that stays current

## Problem

The five triage pages (`fr triage render`, `board`, `origins render`, `architecture render`, `history render`) have grown into long, flat documents. They are hard to scan, they do not link to each other or to the PRs they mention, and some of them are out of date without saying so.

## Requested changes

### Across all pages
- **Harmonize page names and filenames.** The nav says Backlog, but the file is `triage.html`. The nav says Batches, but the file is `board.html`, while the `board/` fragment directory belongs to `triage.html`. A page's title, its file, its command and its fragment directory should share one name.
- **Collapsible sections.** This pattern applies to every page: for example Needs you now, the origin groups and the snapshot timeline. Use one shared component in `components.py`, the same way `tabs()` works today.
- **Links.** Every PR and issue reference links to the forge. A wave reference links to that wave on the page that holds it. For example, "wave XX" in Next up jumps to that wave's tab.

### Backlog (`triage.html`)
- **Too much on one page.** Consider a more sensible split, for example sub-pages.
- **Waves filter.** Allow selecting several kinds at once (defect, feature, parked, unkinded) to show or hide them.

### Batches (`board.html`)
- **Collapsible columns.** Every column can be collapsed and expanded interactively, not only the empty ones that are collapsed today.
- **Optional wave cutoff.** By default, show the waves that were active in the last month.

### Origins
- **Collapsible sections** for each origin group (new-feature, regression, …).
- **More detail for each PR,** not just the reference.
- **"Every issue" filter:** open only, closed only, or all.

### Architecture
- **"The pipeline and its driver, with open issues on the steps they break"** should go back to being **one graph with dated tabs above it**. Clicking the tabs steps through the dates in order.

### History
- **The snapshot timeline is collapsible.**
- **Each PR shows a short summary** as well as its link.
- **The page must stay current.** Today it does not. See below.

## Does History have a logic behind it? (findings, current main)

It is generated, not hand-written, but it is only regenerated by hand:

- `fr triage history render` (`packages/fr/src/fr/triage/history.py`) builds it from two live inputs:
  - the snapshot timeline: the snapshots `fr triage render` stores, keeping the latest `KEEP = 30` (`snapshot.py`);
  - the finished waves: `views.finished_waves` over `judgements.yaml`.
- After those, it adds the authored fragments that `history/manifest.yaml` lists. In this scope those are three hand-written pages, all dated **2026-10-02**: `closing-order.html`, `origins-2026-10-02.html` and `history-2026-10-02.html`. Those are the one-off part.
- **Nothing re-renders it.** The wave driver refreshes only `board.html`. In this scope, `history.html` (like `triage.html`, `origins.html` and `architecture.html`) was last written on **2026-11-14**. Its finished-wave tabs stop at wave 12, while `judgements.yaml` has batches in waves 1–21.
- **The timeline is also thin.** A snapshot is stored only when `fr triage render` (the Backlog) runs. There are 16 snapshots, the newest from 2026-11-14, so the driver's own passes leave no history at all.

So the page has a design, but it is fed only by manual renders, and its narrative half is a one-off from October. The decision this issue needs: either
1. **keep it alive.** The driver (or `board --watch`) re-renders the pages that depend on judgements, and stores a snapshot when a wave finishes. The dated authored fragments move under a clearly labelled "archived notes" heading or are retired; or
2. **retire it.** Fold the finished waves into the Batches page's wave cutoff (above) and drop the snapshot timeline.

Whichever option is chosen, **every page should state when it was rendered**, so a stale page is visibly stale.
