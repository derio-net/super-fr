# Journal: gates-agents-architecture

<!-- fr:journal kind=discovery scope=spec id=brief created=2026-10-23T04:58:11+00:00 input=true -->
### brief · discovery · Operator brief: gates manned by agents, workflows beyond software, architectural decomposition

super-fr has become so much more that I envisioned at the start. It has multiple subsystems, extensibility, protocols, testing & self-correcting disciplines. I'm very happy with it but at the same time I feel its limitations. Things I'd like to do but can't: Have Gates, manned by different Agents that handle Issues and route them dynamically. Architect, Designer, Business Analyst roughly "do" fr-brainstorming, Developer to fr-debugging and parts of fr-goal, DevOps now has fr ops, Tester the Test Plan. These map to Quality Gates that can be either fully or semi-autonomous. We have built flows (fr-goal and fr-goal light) using code that I think is an underutilized "innovation". We could be making so many different workflows, and for many different processes, not only software. I could envision an Editor where we can visually create flows from Gates and Agents. fr-goal allows us to "break" a run into parts by starting subagents, but still, they only start inside the same Claude or Opencode session. A true multi-agentic and even multi repo fr-goal could looks something like: An issue reaches at the Implementation Gate, a mid-level (Sonnet?) coordination Agent picks it up and figures out the next steps, then gives the brainstorming part to a high-level (Opus? Sol?) Agent at the Business Analyst Gate. Once it's cleared the Gate, the coordination Agent reads the Plans and routes it to the Implementation Gate to be picked up by other Agents. The coordination Agent watches that all Phases of the Plan(s) are implemented and places the PRs at the Merge Gate (manned by the DevOps Agent) and finally at the QA Gate (manned by the Testing Agent). We have a DAG graph as part of the fr-plan so the mechanism is there (although we don't really use it any more since we stopped using VK). A fr debugging flow would be similarly routed. Other flows (based on skills or not) could be created, like an fr grill-me or an fr deep-practical-book to run through the system. 
I'm not sure whether this current shape of super-fr would be suitable though, having it incorporate so many different systems. Maybe an architectural rework/decomposition would be necessary, each with clear goals and at different levels, before we proceed. I'm not sure that all super-fr's feature belong at the skill/harness-plugin level. Also, I'm not sure whether our backlog already have similar ideas/proposals so we'd need to have a look there, first, to avoid duplicating or building competing/incompatible features.
