# The `fr run` cursor tells the truth about what it is waiting for

Spec: `docs/superpowers/specs/2026-09-20-fr-run-cursor-cluster-design.md`
Issues: #499, #501, #500, #496 — one PR.

## Why these four travel together

They are not four unrelated papercuts that happened to be filed on the same day. Three of them
live in one function's neighbourhood (`_advance_group` / `advance_cmd` in
`packages/fr/src/fr/commands/run_cmd.py`) and two of them are the *same defect twice*: a fact
that exists upstream is narrowed away at exactly the point where it would have been
load-bearing.

- #499 — `fr run status` knows a member is `running`; `_advance_group`'s pending-picker asks
  only `items.get(key) != "done"`, so `running` and `pending` are the same thing to it.
- #496 — `_group_phases` parses the plan that carries each phase's `tag`, then returns bare
  phase numbers, so `for_each: phase` treats a typed set as homogeneous.

Splitting them across PRs would mean touching `_advance_group` three times and re-reading the
same 200 lines each time. Shipping them together also lets phase 2's `_resolve_hint` and phase
4's `_trailing_manual_block` each have exactly one definition, shared by the two surfaces that
would otherwise drift.

## Phase order, and why the skeleton is #501

Phase 1 is the walking skeleton and it is deliberately the smallest of the four: an error
message. That is the point. It touches `_find_step`, `_advance_group`'s output, one test file
and the whole CI gate — so by the end of phase 1 we have proved that lint, types, the full
suite and a CLI test that reaches the real runtime (not a mock) all work, *before* phases 2
and 5 start rewriting the state machine.

Phase 1 also produces `_resolve_hint`, which phase 2's refusal reuses, so the "how do I resolve
this?" command is rendered in one place from the start rather than being unified later.

Phases 2, 3 and 4 are independent of each other and each depend only on phase 1. They are
listed in issue-severity order, not dependency order — #499 is the one with a real
double-dispatch hazard behind it, so it goes first.

Phase 5 depends on phase 4 rather than merely following it: the `implement` preflight imports
`_trailing_manual_block` from `self_review`'s module so that the authoring gate and the runtime
gate cannot disagree about what "trailing" means. That is a genuine dependency, not sequencing.

Phase 6 is above this plan's ideal phase count and is here anyway, because
`.claude/rules/explainers-currency.md` makes it mandatory and procedure-heavy: the published
page is generated by a renderer that lives in *another repo*, the regeneration has a
`--isolated --no-project`-from-`/` incantation that has silently produced hundred-line spurious
diffs twice, and the rule requires verifying the renderer against the *unmodified* source
before touching a word. Folding that into phase 5 would have buried it.

## What the operator decided (journal `d1`–`d7`)

The batched Q&A settled four things, and one of them reshaped the design:

**#496 was reframed by the operator.** The original three options were all runtime behaviours —
skip it, record it, or add a `deferred` resolve state. The operator's question ("why should a
manual phase be in a `for_each` at all?") turned it into a *structural* question: where may a
manual phase sit? An invariant can be checked before anything runs; a behaviour can only be
observed at dispatch. So the primary enforcement is a `severity="error"` in
`fr.plan_ops.self_review` — which fr-goal already runs as its `plan-review` step, a `kind: cli`
step whose exit code is the verdict — and the run model's job shrinks to "never build a brief,
never hide the omission".

The rule that survived is not bare position. It is **"no manual phase may be outstanding when
an agentic phase after it runs"**: trailing block, *or* already `plan_locally_complete`. That
second clause is what keeps fr-goal §3's front-load exception expressible, since that flow ends
with the operator ticking the phase's steps before implementation resumes.

Spec §1.4 records the measurement that made this cheap: 4/4 live plans, 80/80 archived plans
and 16/16 on-disk fixture plan folders already satisfy the invariant. Zero exceptions. The rule
codifies how this repo already writes plans; it does not ask anyone to change.

## This plan is its own fixture

Phase 7 is a back-loaded `[manual]` phase — fr-goal's documented default. So the plan that
implements "a manual phase must be trailing and is never dispatched" is itself a plan with a
trailing manual phase, which phase 5's own code has to handle correctly in order for this run
to reach its PR. That is not a cute coincidence to lean on, but it is a real end-to-end check
that arrives for free, and phase 7 is where it gets confirmed deliberately.

## What is deliberately not here

- No third `fr run resolve --state` value. §3.D removes the need: no brief is built, so there
  is no outcome to record.
- No change to the shipped `fr-goal` shape's step list. `_check_step_drift` refuses to advance
  any run started against a different list, so adding a `manual` step would restart every
  in-flight fr-goal run for something the items map already delivers.
- No change to `fr_dispatch` / `fr_vk`. The bridge's item-level reachability gate is a
  different axis and is untouched.
- No tripwire for third-party redaction. Phase 7 captures live evidence and the redaction
  discipline in `.claude/rules/third-party-privacy.md` is prose-only by that rule's own
  admission; the phase says so in its own step rather than implying automation that is absent.
