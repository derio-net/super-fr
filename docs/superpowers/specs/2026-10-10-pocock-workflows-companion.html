fr meets Pocock

Matt Pocock's skills tell an agent how to think at each stage of a change: how to interview you, how to slice the work, what a good test and a good review look like. fr decides where the work happens and what must be true before it moves on: an isolated workspace, a cursor that refuses steps out of order, and journals and gates that prove a review happened. Most of the two fit together. They clash only where both try to own the same decision.

compatible: fr already does this, in different words opposite in spirit: one has to give way enhance: each covers something the other lacks

Compatible, opposite, enhancing

Compatible

Spec before code

Both turn the conversation into a spec that later work is checked against: Matt's code-review Spec axis, fr's "the spec is the contract".

Tickets are phases

Vertical tracer-bullet slices with blocking edges match fr phases with depends_on. Matt's "frontier" is the set of phases whose dependencies are done.

A fresh context per unit

/clear between /implement tickets is the same move as one fr-phase-executor subagent per phase.

Test first, one slice at a time

tdd's red → green per slice is fr-execute's TDD-shaped step.

Parallel work on isolated branches

implement-spec runs implementers in their own worktrees and merges to an integration branch. fr does the same with its isolation worktree and fr apply --to <runner>.

Review in a separate context

Matt's review sub-agents and fr's dispatched reviewer share a principle: the implementer never reviews its own work.

Bugs start with a red reproduction

diagnosing-bugs refuses to theorise without a loop that goes red. fr-debugging puts root cause before fix. Both end with a regression test.

Harness-neutral text

Matt rejects harness-specific branches in his skills. fr has a tripwire that fails on harness-specific tool names in skill prose.

Opposite in spirit

Who owns the process

Matt positions his pack against frameworks that own the process and take away your control. His skills are small, and you're meant to hack them. fr's cursor owns the order and refuses a step taken out of turn.

How many questions

Grilling has no cap by design. A cap request is explicitly out of scope: some plans need three questions, some need fifty. fr-goal asks one round sized to the goal, rarely two.

Where the human sits

Matt checks in at the grill, the seams, the ticket cut and the retro. fr-goal waives gates and runs unattended to the PR.

Prose versus code

For Matt, natural language is the control surface, and stopping runaway loops is the harness's job, not the skill's. For fr, an obligation enforced by an instruction gets absorbed under load, so it uses tripwires, evidence gates and refusals.

Where refactoring goes

tdd: Refactoring is not part of the loop. It belongs to the review stage. fr's phases are red → green → refactor, and a refactor gate checks it.

What a spec may name

to-spec: Do NOT include specific file paths or code snippets. fr specs name modules and files, and its spec reviewer checks the spec against the code they point to.

Where the record lives

For Matt it's the issue tracker: the spec issue, ticket issues, triage labels. For fr it's files in the repo: the spec, plan, journal and cursor, which the gates can read offline.

Weight per change

Matt's flow leaves a few markdown files and a PR. An fr run adds cursor commits, step records, journal entries and a usage file.

Coexist and enhance

A shared vocabulary

domain-modeling's GLOSSARY.md and ADRs fill a gap in fr, which has no domain-language layer. Specs, reviewers and executors would all read them.

Grilling that leaves a record

Matt supplies the interview: design tree, frontier, a recommended answer for each question. fr makes each answer a journal decision that the spec reviewer checks the spec against.

A review you can trust

code-review's two axes and smell baseline tell the reviewer what to look for. fr's evidence gate proves the review ran, and nothing it found was quietly dropped.

A better PR body

Matt adds the smallest visual, before/after evidence and the one-way or two-way door call. fr adds the findings, the operator gates, proportionality and cost.

Retro meets tripwires

retro's rule that a mechanical violation gets a deterministic check, full stop, is fr's own rule. Retro findings could become journal entries or triage issues. fr-audit adds the cost data retro can't see.

Seams and acceptance rows

The seams tdd agrees up front are where the acceptance matrix's business-level rows get their test refs.

Cheaper boundaries

fr's cursor and fr pickup carry the state of the work across a clear or a restart, which takes most of the risk out of Matt's /clear-versus-/compact decision.

Debugging with rails

diagnosing-bugs' red-loop discipline inside fr-debugging's isolation, debug journal and reviewed PR.

Surveys that feed triage

The deepening candidates improve-codebase-architecture finds become issues for fr-triage to rank and batch.
