# Repo feature settings and artifact placements — design

**Date:** 2026-11-04
**Slug:** `2026-11-04-repo-feature-settings`
**Status:** design (fr-brainstorming, standalone)
**Repo:** `derio-net/super-fr` (single-repo change, three plans)

## 1. Background

super-fr assumes every repo it works in wants the whole paper trail, and puts
all of it on the feature branch:

- spec, plan folder, journals, run cursor;
- the acceptance matrix and its three committed reports;
- a Test Plan;
- gate labels and an fr-rendered PR body;
- `chore(fr):` commits, plus pushes and draft PRs opened without asking.

The operator named four situations where that is wrong:

1. **Shared or third-party repos.** Teammates don't use super-fr, and fr's files,
   commits, labels and PR sections are noise to them, or leak process detail.
2. **Lighter process.** The ceremony costs more than it returns.
3. **Different conventions.** The repo keeps specs, tests or acceptance
   elsewhere.
4. **Forge-side quiet.** Labels, issues, comments and PR sections are the most
   visible traces of all.

Two read-only surveys of the code (2026-11-04), plus the spec review, found:

**Configuration that already exists**

- No setting addresses this. The only env skips are `FR_SKIP_MIGRATION` and
  `FR_SKIP_IDENTITY`.
- `tracking: none` (the tracking service in `.devcontainer/fr-profiles.yaml`,
  read by `fr.services.resolve.resolve_tracking` and
  `fr.services.require.require_tracker`) is honoured in 18 modules: label sync,
  awaiting-live labels, backfill trackers, `fr journal file`, archive filing,
  `fr debt`, the PR body's owed sections, and others. It does not govern
  comments, and it does not touch any in-repo trace.

**Paths and detection**

- About 44 modules hardcode `docs/superpowers/…` or `docs/acceptance/…`, as do
  the shell hooks.
- The registry locators (`fr.artifacts.registry`) are read only by migration,
  the trigger and `fr validate artifacts`.
- Two places decide whether a repo is "fr-enabled": the bash decision library
  (`plugins/super-fr/hooks/lib/fr-isolation-decision.sh`) and the OpenCode
  plugin (`packages/fr-opencode-plugin/src/marker.ts`). Each does it separately,
  from a devcontainer profile or a `docs/superpowers/plans/` directory.

**The matrix**

- The matrix is one shared file, the `matrix` kind (v5). Its single-file
  locator is `docs/acceptance/matrix.yaml`.
- Its three committed reports are regenerated by every feature.
- github.com shows a committed `.html` as source, so only `report_linked.md`
  ever rendered for a reader.

**Seams the design leans on**

- `operator_answered_since` (`fr/run/telemetry.py`) reads the session
  transcript. It returns `None` when it cannot read it: on Hermes, on an
  unrecognised harness, and on an OpenCode session it cannot export.
- `_deliver_pr_gate` (`commands/run_cmd.py`) renders `pr-body.md`, checks the
  live PR against it, then deletes it. The PR itself is created by the agent,
  running the command fr prints.
- Runner dispatch's reachability gate (`fr/workflow/reachability.py`) reads
  `origin/HEAD`.
- A run cursor records no issue.

## 2. Philosophy analysis

Each artifact does two jobs:

- it is the pipeline's **working memory**: the spec is the contract, the plan
  feeds the phase executors, and the journals are the only proof a phase was
  reviewed;
- it is a **durable trace** in the product repo.

The surveys sort the features accordingly:

| Feature | Absent today | May be off? |
|---|---|---|
| Acceptance matrix | Degrades everywhere | **Yes**: a policy a repo may decline |
| Test Plan | Never refused (only a near-miss heading is) | **Yes**: a policy |
| Gates | No gate lines means nothing holds | **Yes**, except that a plan with ops forces `devops`, and a row gate needs rows |
| Spec, plan, journals, run state | fr-goal's emit, `needs` and review-evidence gates refuse | **No**: fr-goal cannot run without them |

The decisions that follow:

1. **Memory kinds are never off, only placed.** The settings schema has no key
   that could turn them off.
2. **A policy kind that is off is reported, never silent.** It shows as
   "disabled by repo setting", never as "none".
3. **Some things are never settable.** No setting marks a PR ready, merges it,
   or force-pushes a feature branch. The DevOps gate's existing `--force-with-lease`
   push of its own ops branch, at the operator's terminal, predates this spec
   and is out of its scope.
4. **Squash keeps evidence and pushed history intact.** fr's evidence binds to
   code trees, not commits (`fr/run/code_tree.py`, `fr/verification/walk.py`),
   so a squash orphans none of it. Pushed history is pinned by the DevOps gate's
   `head_oid`, by the review-ok guard and by `tests: ci`, so squash folds only
   unpushed commits.
5. **Placement must travel with the work.** A placement that lives on one host
   fails on the next, which would see nothing and write traces. So every
   placement's switch and settings live with its artifacts, and there is no
   host-local settings layer.
6. **A guarantee is stated only as strongly as its mechanism enforces it.**
   Where fr cannot observe what a gate needs, the gate refuses. Every control
   this spec adds needs a seam fr owns.

## Requirements

### Placements and settings

R1. Every artifact fr writes has one of three placements:

| Placement | Where the artifacts live |
|---|---|
| `repo` (default; today's behaviour) | on the feature branch |
| `quiet` | on one orphan branch named `fr` in the same remote, each feature under its own path |
| `stealth` | on a branch of a separate tracking repo |

One path resolver, keyed by kind and placement, produces every artifact path.
It covers the Python modules, the shell hooks, the OpenCode plugin, the Hermes
hook and the shipped CI templates. A tripwire refuses a hardcoded artifact
path outside it.

R2. Settings live with the placement, and there is no host-local layer:

| Placement | Where the settings file lives |
|---|---|
| `repo` | an optional committed `.fr/settings.yaml` |
| `quiet` | `settings.yaml` at the root of the `fr` branch |
| `stealth` | the tracking repo, one file per target |

The policy keys (`artifacts.*`, `forge.*`, `git.*`) are always read from the
default ref's revision:

- `origin/HEAD:.fr/settings.yaml` under `repo`;
- the remote `fr` branch under `quiet`;
- the tracking ref under `stealth`.

A branch that edits them gets no effect until the edit lands there, and the
edit itself is not subject to the policy it changes. A missing key takes its
documented default, and every default is today's behaviour.

The default ref is named fully qualified and read by commit SHA, once, in this
order:

1. **A remote with remote-tracking refs** (any `refs/remotes/origin/*`) reads
   `origin/HEAD`, then `origin/<init.defaultBranch | main | master>`. If none of
   these resolves, fr refuses with the fix (`git fetch`, `git remote set-head
   -a`). A local branch is never read here, because it may carry unpushed edits
   to the remote's policy.
2. **No remote at all** reads the local `refs/heads/<init.defaultBranch | main |
   master>`. If no such branch exists, there are no commits to hold a policy, so
   fr uses the defaults and prints a note.
3. **A remote with no tracking refs yet** (added but never fetched or pushed)
   uses the built-in defaults and prints a note naming that state, so a fresh
   repo works offline. It never reads a local branch: deleting tracking refs
   must not hand the policy to a branch that `init.defaultBranch` picks.

A file that exists at the resolved commit but cannot be read refuses. It is
never read as absent.

There is one exception: a CI context (any truthy CI marker fr's migration gate
already reads) whose checkout has no default ref, such as a depth-1
pull-request checkout. There fr reads the file from HEAD's committed tree (never
the working tree) and prints one notice naming that source. CI's checkout is the
candidate merge itself, so a PR that edits `.fr/settings.yaml` shows the edit in
its own diff. Refusing there would turn every consumer's existing CI red on
upgrade.

A settings refusal is always a clean message and exit 2, never a traceback.

R3. The `fr settings` commands:

- `fr settings init` writes the placement's file, with every key commented out
  at its default and a comment stating its allowed values, what the default
  does, and what the non-default trades away.
- `fr settings show` prints the effective settings and each key's source.
  `--json` prints them for skills.
- `fr settings paths --shell` prints the resolver's answers for the hooks.
- `fr settings check` validates.

R4. The schema is closed. Every fr command that reads settings refuses, naming
the file and the key:

- an unknown key or value;
- a schema newer than this `fr`;
- a placement that this `fr` cannot yet serve.

That last refusal happens in the loader, not only in `check`. The policy kinds
`acceptance`, `test_plan` and `gates` take `on` or `off`. The memory kinds have
no key.

R5. `fr settings check` and `fr run start` refuse incoherent settings, naming
the conflict:

- `gates: off` when a live plan carries manual operations;
- `push: ask` for a scope driven by `fr triage batch drive`, which is
  unattended by design;
- under `stealth`, any explicit forge key other than the quiet value. Stealth
  sets those keys itself, and an explicit contrary value is refused rather
  than ignored.

### Policy off

R6. Under `acceptance: off`:

- fr writes no fragment, no report, and no matrix CI.
- `fr acceptance add` and `set-status`, and any record's `acceptance:` section,
  are refused, naming the setting.
- Brainstorm presents no rows.
- A row-level `gate: <row>=<gate>` line is refused. A run-level `gate:` line
  stays valid.
- Walk evidence is the run-bound walk log only, with no row write.
- Self-review, the PR body, `fr debt`, proportionality, `fr acceptance status`
  and the SessionStart nag all say "disabled by repo setting".

R7. Under `test_plan: off`:

- The brainstorm writes no `## Test Plan`.
- A spec carrying one is refused when the `brainstorm` or `spec-review` step
  resolves, and by `fr validate artifacts`, naming the setting.
- Close-out and archive owe no Test Plan outcomes.
- The staleness guard does not require rows that cite a Test Plan.

R8. Under `gates: off`:

- No gate is computed, labelled or held.
- A spec whose `## Verification` carries a `gate:` line is refused at the same
  points as R7.
- Verification strategies and walks still run.

### Forge quiet

R9. `forge.labels`, `forge.comments` and `forge.issues` each take `on` (the
default) or `off`. One predicate, `fr.settings.forge_allows`, replaces every
existing `tracking: none` check and covers the sites that check misses.

Under `off`, fr makes no forge write of that kind anywhere, including from the
CI it scaffolds, such as the "Acceptance debt" issue step. A leftover that would
have been filed stays recorded in the journal, and `deliver` accepts it as
recorded. `tracking: none` keeps meaning all three are off for tracker work
(issues, and their labels and comments).

The PR gate ledger is the one exception. It covers the `gate:*` and
`gate:*-passed` labels and the gate-pass comments on a pull request, which the
release gate and the DevOps stage read. That ledger answers only to
`forge.labels` and `forge.comments`, and `deliver`'s label sync, `fr gate
pass`, `fr gate backfill` and the driver's pass all apply this one rule.

Reads are never gated. A command acting on a repo it has no checkout of
(`--repo`, a triage scope) reads that repo's `.fr/settings.yaml` at its default
branch through the forge's contents API. If the file is absent, the defaults
apply. If the read fails, the write is refused. Policy is never assumed.

A tripwire lists every forge write call site in `packages/*/src` and fails on
one that consults no `forge_allows`.

R10. `forge.pr_body` is `full` (the default) or `minimal`. Under `minimal`:

- The live PR carries only a plain summary, with no fr marker, section or
  table.
- The full body is kept as a durable artifact in the active placement:
  `<run>.pr-body.md`, not deleted at `deliver`. `deliver` prints its path as
  what the operator reviews: findings, owed rows, and the historical-review
  list.
- `deliver` still checks the live body for every shared closing keyword, and
  refuses any fr marker in it.

### Git policy

R11. `git.push` and `git.pr` each take `auto` (today's behaviour) or `ask`.
Under `ask`, each push or PR creation fr performs proceeds only on a verified
operator answer given after its request was printed.

- The approval is recorded as a decision with `answered_by: operator` in the
  run's own journal: the spec journal of a spec-driven run, the debug journal of
  an fr-debugging session, which has no spec.
- The verified answer is an answered question, asked after the request, whose
  text names the request's id. The request names the option to offer,
  `Approve <request-id>`, and the answer to that question, read as a
  (question, answer) pair, must equal it exactly after trimming whitespace.
  Answers to other questions are ignored; any other answer is refused, naming
  it.
- Where fr cannot read the transcript, or cannot pair the answers with their
  questions, the request is refused, naming the harness. The `--no-questions` bypass does not
  apply.

Marking a PR ready and merging it are not settable.

R12. Two new commands own the skill-driven remote writes:

- `fr push` makes every push of a run's feature branch;
- `fr pr create` makes every PR creation, always as a draft.

The skills call them instead of `git push` and the forge CLI. `deliver` refuses
a PR that `fr pr create` did not open, when `pr: ask` is set. fr's own internal
pushers are outside these two commands, and the spec states each one:

- the triage driver, which R5 refuses under `push: ask`;
- the DevOps gate, at the operator's terminal;
- the state-ref pushes.

R13. `git.history` is `keep` (the default) or `squash-unpushed`. Under
`squash-unpushed`, `fr push`:

- folds the commits that are not on the remote branch, or, on a branch's first
  push, the commits since its merge-base with the default ref;
- splits that range into segments at every merge commit and every
  `chore(fr): migrate …` commit, keeps those commits as they are, and squashes
  each segment into one commit;
- never rewrites a pushed commit and never force-pushes;
- leaves the final code tree unchanged.

R14. `git.commit.with_issue` and `git.commit.without_issue` are subject
templates over a closed placeholder set: `{type}`, `{scope}`, `{summary}` and
`{issue}`. An unknown placeholder is refused, and so is `{issue}` in the
without-issue template.

- The with-issue template applies when the run records an issue: a new
  optional `issue` on the run cursor, set by `fr run start --issue <n>` and by
  triage batch dispatch.
- fr's own commits use the templates.
- The briefs and `fr pickup` carry them to the agents.
- `fr push` refuses an unpushed non-merge commit whose subject does not match.
  Merge commits are exempt.
- A scope is optional only in the Conventional Commits shape: when every
  `{scope}` follows `{type}` and opening brackets (`{type}({scope})`), that
  unit with its brackets matches an absent scope and renders as nothing when
  the scope is empty, so `test: x` matches `{type}({scope}): {summary}` and
  fr never writes `test(): x`. Anywhere else (`[{scope}] {summary}`) the
  template's author asked for a scope, so it is required. `{type}`,
  `{summary}` and `{issue}` are always required, so `Fix typo` still refuses.
- Under `squash-unpushed`, fr composes the subject itself.

R15. Every shipped skill that writes, nags about or renders a configurable
feature reads the effective settings (`fr settings show --json`, or its
brief) instead of assuming the defaults.

### Acceptance model (every placement)

R16. Acceptance rows live in per-feature fragments, and each row is owned by
the feature that created it. A later feature changes an existing row only by
appending an amendment to its own fragment: `reword`, `set-status`,
`add-level`, `drop-level` or `retire`.

These are written through `fr acceptance add`, `fr acceptance amend`, and the
record's `acceptance:` section, which gains an amendment shape.

R17. The effective matrix is never stored. It is a fold over amendments from
merged features, ordered by the first-parent commit of the default ref that
introduced each amendment. A branch's view adds its own pending amendments.
An abandoned feature's amendments never apply.

Each amendment names the row revision it is based on, where the revision is
the count of amendments applied to the row. The stale-base rule:

- Before merge, `deliver` and CI fetch the default ref and refuse an amendment
  whose base is stale.
- A stale amendment that merged anyway applies in order, and marks its row
  **contested**, which is debt.
- The next amendment from any feature, based on the row's current revision,
  clears it.

Under `quiet` and `stealth`, a feature's merged status and order come from its
code branch's merge into the product's default ref. `merged:` records are a
cache, never the truth.

R18. Rows reference fr artifacts logically (`spec:<slug>#R<n>`,
`plan:<slug>`). Code references keep `<repo>:<path>#<test>`.

- Until plan 3, logical references resolve to `repo` paths only.
- From plan 3, they resolve through R1's resolver.

A placement move never rewrites a row.

R19. `fr migrate artifacts --yes` migrates an existing repo to fragments:

- It splits `docs/acceptance/matrix.yaml` by origin spec. Rows without exactly
  one origin go to a `legacy` fragment.
- It converts path references into logical ones.
- It deletes the committed reports.

The new `acceptance-fragment` kind has its own locator
(`docs/acceptance/features/*.yaml`). The `matrix` kind is retired after its
last migration, with a frozen reader of v5. The `record` kind's stamp moves for
the amendment shape. Each kind ships a stamp, a migration and a structure
validator.

R20. Reports are derived, never committed:

- `fr acceptance report [--open]` renders them locally.
- The README's "Viewing the acceptance report" section and `fr --help` name
  that command.
- Under `repo`, the CI fr scaffolds publishes them:
  - a job summary on every PR (GitHub Actions and Gitea Actions);
  - an exposed artifact (GitLab CI);
  - the HTML report on Pages from the default branch, with a link or badge in
    the README.
- Under `quiet` and `stealth`, fr scaffolds no CI, no Pages and no badge;
  reports are local only.

R21. Pages publishing is scaffolded only where the site can be no more
visible than the repo:

- either the repo is public;
- or the forge reports access-controlled Pages: GitHub `GET /repos/{o}/{r}/pages`,
  or GitLab's project `pages_access_level`.

fr fails closed. No Pages job is scaffolded wherever it cannot read
visibility, which covers Gitea and any read failure, and the README badge then
points to the latest default-branch CI run. The published job re-checks
visibility before every deploy, and skips the deploy when the check fails.

R22. `forge.report_comment` is `off` (the default) or `on`. When on, CI keeps
one PR comment carrying the Markdown report. It requires `forge.comments: on`,
and is refused under `quiet` and `stealth`.

### Quiet and stealth

R23. Under `quiet`:

- **The switch.** The `fr` branch is an orphan branch whose root
  `settings.yaml` carries `placement: quiet`. fr reads it from
  `refs/remotes/origin/fr`, fetched at `fr isolation up` and at `fr run start`,
  and refuses both when `origin` is unreachable. A repo with no `origin` is
  `repo`.
- **Sticky.** The placement is recorded in the workspace's isolation state at
  `up`. A later disagreement refuses, naming both values, which covers a
  deleted or renamed `fr` branch.
- **Known limitation, stated in docs and in `init --quiet`.** A host whose fr
  predates plan 3 never looks for the switch.
- **Append-only history.** Commits on `fr` are never rewritten or
  force-pushed. Each commit touches only one feature's path, or the root
  `settings.yaml`.
- **Pushing.** When code moves, `fr push` pushes the feature branch and `fr`
  together with `git push --atomic`. On a rejected `fr`, it fetches, replays
  its own fr commits onto the new tip (the paths are disjoint), and retries.
  Bookkeeping written after the last code push is pushed to `fr` alone, the
  same way.
- **Nothing on the product branches.** No fr artifact and no `chore(fr):`
  commit reaches the default branch or any feature branch.
- **Not available here.** Runner dispatch (`fr apply --to`) is refused under
  `quiet`, naming the placement.

R24. Stealth is chosen per run, never by repo settings, in one of two ways:

- fr-goal or fr-debugging is invoked with `mode=stealth`, naming the tracking
  repo and branch;
- the run is started from the tracking repo with `mode=stealth`, naming the
  local target.

**The local record.** The workspace's isolation state and its `.fr-isolation`
marker record `placement: stealth` and the tracking ref. Every fr command, hook
and skill run in that workspace reads them, so no command run there falls back
to `repo`.

**Fail-fast.** fr refuses before any write when the tracking repo or branch is
missing or unreachable. Every state write checks reachability, and a failed
tracking push refuses the step's resolve: it is never only a warning.

**What reaches the target.** Only the code commits and one draft PR with a
minimal body. No fr file, commit, label, comment or issue reaches it. When the
target carries a `.fr/settings.yaml`, the tracking repo's file wins, and fr
prints that the target's file was ignored.

**Privacy.** The privacy guard (`fr.triage.privacy.leak_risk`) refuses a
tracking repo more visible than the target.

**Resume.** A run is resumed from the tracking repo, which records the target's
remote and branch. The order of writes is fixed: code is pushed before state,
and the state records the product head it describes. On resume, fr reconciles
the two:

- equal → resume normally;
- the branch is ahead → redo the last step's bookkeeping;
- the state is ahead → refuse, naming the missing SHA.

Runner dispatch is refused, as under `quiet`.

R25. How a merged feature is archived:

- under `quiet` and `stealth`, archive appends a `merged: <sha>` cache record
  to the feature's path and moves nothing;
- under `repo`, it keeps `implemented/`.

R26. The fr-enabled tests treat two more cases as fr-enabled: a valid `fr`
branch switch, and a workspace whose isolation state records `stealth`. The
tests covered are the bash decision library, the OpenCode plugin and the
Hermes hook, each with its `parity.yaml` row.

### Moving between placements

R27. `fr placement move --to repo|quiet|stealth [--tracking <repo>@<branch>]`
moves a whole repo, including archived features and the shared artifacts of
live runs. `--run <id>` moves one stealth run.

- **Steps.** Copy, then verify, then switch, then remove. Verify means the
  destination's folds and `fr validate artifacts` equal the source's. A move
  into quiet or stealth from repo synthesises `merged:` records from the
  default ref's history.
- **Restartable.** Every step is idempotent and resumable.
- **History.** A move out of `repo` removes the files from the default branch
  through a PR, and prints that git history still holds them.
- **Precondition.** A move is refused while any workspace has uncommitted
  work.

R28. A feature branch whose artifacts do not match the repo's current
placement must migrate before it can merge. A dedicated command,
`fr placement migrate-branch`, run in a valid workspace, does the migration as
its own commit, and pushes the moved artifacts where they belong.

The CLI-entry gate only detects the mismatch and refuses, naming that command.
So do `fr push`, `deliver`, and, where fr's CI exists, the `validate-artifacts`
job. CI never migrates.

### Delivery

R29. Three plans, three PRs:

| Plan | Scope | Requirements |
|---|---|---|
| 1 | Settings core, `repo` placement only | R2–R15. `init --quiet`/`--stealth`, R5's stealth rule and R23's atomic push wait for plan 3. |
| 2 | Acceptance model and derived reports | R16–R22, with R18's interim repo-only resolution |
| 3 | Resolver, quiet, stealth, moves | R1, R23–R28, plus the quiet and stealth parts deferred from plan 1 |

Until plan 3 lands, the loader refuses `quiet` and `stealth` as "not yet
available".

## 3. Design

### A. Settings (R2–R5)

```yaml
# .fr/settings.yaml (repo) · <fr branch>/settings.yaml (quiet) · <tracking>/<target-id>/settings.yaml (stealth)
schema: 1
placement: repo            # repo | quiet | stealth   (must match where this file lives)
artifacts:                 # policy kinds only — spec/plan/journals/runs have no key: never off
  acceptance: on           # on | off
  test_plan:  on           # on | off
  gates:      on           # on | off
forge:
  labels:   on             # on | off
  comments: on             # on | off
  issues:   on             # on | off
  pr_body:  full           # full | minimal
  report_comment: off      # off | on   (needs comments: on; refused under quiet/stealth)
git:
  push:    auto            # auto | ask
  pr:      auto            # auto | ask   (always a draft; ready/merge are never fr's)
  history: keep            # keep | squash-unpushed
  commit:
    with_issue:    "{type}({scope}): {summary} (#{issue})"
    without_issue: "{type}({scope}): {summary}"
```

A new `fr/settings/` package:

| Module | Job |
|---|---|
| `model.py` | closed pydantic model |
| `load.py` | placement discovery, then the default-ref revision; refuses unservable placements |
| `check.py` | R5, as data |
| `render.py` | `init`'s comments, generated from the field docs |

- **Trigger exemption.** `settings` joins `READ_ONLY_COMMANDS`, under the
  criterion's own words: it never mutates a registered artifact.
  `init --quiet`/`--stealth` write a remote branch, which is not an artifact.
  The pinned exemption test (`test_the_exemption_list_is_exactly_these_things`)
  is updated.
- **Predicates.** Callers ask `fr.settings.disabled(root, feature)` and
  `fr.settings.forge_allows(root, kind)`. A grep of `resolve_tracking`,
  `require_tracker` and `tracking … none` lists the sites that move to them.

### B. Policy off and forge quiet (R6–R10)

- **Where off applies.** Each `off` is applied where absence is already handled
  (the matrix loaders, `record/apply.py` `_acceptance_writes`, `spec.py`, and
  `verification/exit.py`). Every "None."/silent branch splits into "absent" and
  "disabled by repo setting".
- **Spec-level refusals (R7, R8)** run in `fr run resolve`'s spec checks for
  `brainstorm` and `spec-review`, and in the spec kind's structure validator.
- **`pr_body: minimal`** (in `_deliver_pr_gate`):
  - keeps the render, at the placement's `runs/<run-id>.pr-body.md`;
  - drops the live-body section check, but keeps the closing-keyword and
    marker checks.

### C. Git policy (R11–R14)

**`fr push`** (`commands/push_cmd.py`) runs, in order:

1. Resolve the run from the branch.
2. Under `push: ask`, require a verified operator decision journalled after
   the request.
3. Squash (R13).
4. Check the subjects against the templates (R14).
5. Push. Under `quiet`, this is an atomic push with the replay-and-retry loop.

**`fr pr create`** (`commands/pr_cmd.py`) applies `pr: ask` the same way,
creates the draft through the repo's forge adapter, and records the PR on the
cursor.

**Skill changes.** fr-goal §6/§8, fr-debugging and fr-execute switch to these
two commands.

**`issue` on the run cursor.** This is a `run`-kind shape change in plan 1: a
stamp, a migration, and an optional defaulted field.

### D. Acceptance fragments (R16–R22)

A fragment lives at `docs/acceptance/features/<spec-slug>.yaml` under `repo`:

```yaml
schema_version: 1
feature: 2026-11-04-repo-feature-settings
rows:
  - {id: repo-settings-file, capability: …, acceptance: …, origin: [spec:2026-11-04-repo-feature-settings#R2], …}
```

- **The fold.** One `fold()` (in `fr/acceptance/fold.py`) is read by `check`,
  `status`, `report`, `debt`, self-review, the PR body and close-out.
  Amendment order comes from first-parent introduction: the fold walks
  `git log --first-parent --reverse` over the fragments. Contested rows are
  debt.
- **The migration.** `acceptance_fragments` is a migration with a frozen
  `MatrixV5` reader. The rule files are rewritten to match: the repo-local
  `.claude/rules/acceptance-matrix.md` and the scaffolded rule.
- **CI templates** live in `fr/acceptance/scaffold.py`. `ci.py` only detects
  CI. Each template gains a per-PR publish step and, after the R21 check, a
  Pages job that re-checks before deploying. A forge visibility reader is added
  to the GitHub, GitHub-REST and GitLab clients. The Gitea client reports
  "unknown".

### E. Placements (R1, R23–R28)

- **The resolver.** `fr.artifacts.paths` replaces the hardcoded constants.
  `ArtifactKind.locator` becomes its `repo` output. The hooks use
  `fr settings paths --shell`. The OpenCode plugin calls the same command, or
  falls back to the plans test only when `fr` is absent, and states that
  fallback at load.
- **Quiet** works through a second worktree of `fr`, at
  `~/.cache/fr/worktrees/<repo>/fr`.
- **Stealth** reuses the mechanics of `fr/triage/state_ref.py`, fetch-before-read
  and compare-and-swap push, with failure made fatal (R24). Each target gets its
  own directory, `<host>--<owner>--<repo>/`.
- **Moves.** `commands/placement_cmd.py` holds `move` and `migrate-branch`. The
  artifact trigger gains a detection-only check that refuses, naming
  `migrate-branch`.

## 4. Non-goals

- Adapters to external systems (Jira, test-case tools, ADR directories). The
  "different conventions" case turns the feature `off` instead.
- A host-local settings layer.
- A setting that marks a PR ready, merges it, or force-pushes a feature branch.
- Moving a stealth run between two tracking repos.
- Runner dispatch under `quiet` or `stealth`.
- Detecting the quiet switch on a host whose fr predates plan 3 (R23).
